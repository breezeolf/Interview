# 招募失败归因：15 分钟的快照陈旧，以及「拿缓存当权威」的校验

> 数据：`recruitment_logs.csv`（1162 行，2026-09-01 ~ 09-07，4 个区服 × 9 个卡池）
> 代码：[analysis/analyze.mjs](analysis/analyze.mjs)（零依赖 Node 脚本，`node analysis/analyze.mjs --check`）
> 产物：[analysis/out/](analysis/out/)（summary.json + 8 张明细表）

---

## TL;DR

1. **失败不是随机的**：已判定样本 1058 次，失败 143 次（13.52%）。卡池时延 ≤15 分钟时失败率 **4.53%**（36/794），>15 分钟时 **40.53%**（107/264），相对风险 **8.94 倍**；25.0% 的请求落在陈旧那一侧。
2. **陈旧不是随机的**：并发在线从 8~31 涨到 72~98 时，陈旧占比从 **8.6% 涨到 49.1%**，四个区服都是同一趋势 —— 同步任务在高峰期被拖垮。
3. **但时延只是「暴露面」，不是根因**：青龙二区同样有 23.7% 的陈旧请求，陈旧请求失败却只有 **6.2%**（4/65），其余三区是 **51.8%**（103/199）。青龙的失败只跟**剩余配额**有关（余量 <5 时 31.5%，≥5 时 **0 失败**）；其余三区相反 —— 余量 ≥20 的陈旧请求照样失败 **57.7%**。
4. **根问题是校验口径**：扣券前的状态校验拿缓存快照当权威，快照一落后就整批判失败；配额其实还有货。修好口径后，按青龙的曲线外推，失败可从 **143 次降到约 84 次（-41.5%）**，约 **4,425 点券 / 7 天**，且不阻挡任何一次本可成功的招募。
5. **如果只能先上一条止血规则**：快照超过 15 分钟就先置灰并触发同步。回测把失败率从 **13.52% 降到 4.53%**，净收益 **+2,745 点券 / 7 天**（置灰 20 点券/次、失败 75 点券/次）；盈亏平衡点是不高于 **30.4 点券/次**，当前 20 点券还有 34% 安全边际。

## 1. 我看到了什么

### 1.1 先排掉三个坑，否则结论会跑偏

| 坑 | 事实 | 不处理的后果 |
| --- | --- | --- |
| 时区 | `action_time` 是 `+08:00`，`pool_synced_at` 是 `Z`(UTC) | 直接字符串相减会得到 **480~545 分钟**的「时延」，于是 100% 请求都「陈旧」。正确换算后是 **0~65 分钟** |
| 重复 | 1162 行只有 **1107 个** `log_id`，55 行整行完全重复 | 失败数会算成 153 而不是 143（+7%），失败率 13.77% 而不是 13.52% |
| 未决 | `is_success` 为空 **49 条（4.4%）** | 当失败算会得到 17.34%，当成功算会得到 12.92%。本文一律**从分母里剔除**，单独列风险敞口 |

> 数据本身很干净：8 列无缺失（除 `is_success`）、无负时延、时间戳格式统一、`log_id` 重复行内容 100% 一致（是流水重复写入，不是玩家重试）。

### 1.2 会失败的请求，几乎都是快照超过 15 分钟的

| 快照时延 | 请求数 | 失败数 | 失败率 |
| --- | ---: | ---: | ---: |
| 0–5 分钟 | 279 | 15 | 5.4% |
| 5–10 分钟 | 277 | 12 | 4.3% |
| 10–15 分钟 | 238 | 9 | 3.8% |
| **15–20 分钟** | 18 | 6 | **33.3%** |
| 20–30 分钟 | 64 | 24 | 37.5% |
| 30–45 分钟 | 74 | 30 | 40.5% |
| 45–60 分钟 | 72 | 32 | 44.4% |
| ≥60 分钟 | 36 | 15 | 41.7% |

- 时延分布是**双峰**：0~13 分钟占 75.0%，17~65 分钟占 25.0%，**14/15/16 分钟一个样本都没有**。
- 门槛效应非常陡：跨过 15 分钟，失败率从 4.5% 直接跳到 40%。
- 时延与剩余配额无关（`corr(remain, lag) = 0.048`，各余量档陈旧占比 19.7%~27.9% 基本持平），所以不是「快卖完了才不同步」。

### 1.3 陈旧从哪来：并发越高，同步越跟不上

按并发在线十分位（各 106 条左右）：

| 并发在线 | 8–31 | 31–39 | 39–44 | 44–48 | 48–52 | 52–56 | 56–60 | 60–64 | 64–72 | 72–98 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 陈旧占比 | 8.6% | 16.0% | 17.0% | 13.2% | 21.7% | 29.5% | 23.6% | 31.1% | 39.6% | **49.1%** |

四个区服分别看，趋势一致（青龙 17.7%→35.1%，朱雀 16.7%→35.4%，白虎 14.5%→39.8%，玄武 19.3%→34.4%，按 55 在线切分）。

**但并发只是「让它变陈旧」的原因**：固定时延看，并发高低对失败率几乎没有影响 —— 新鲜组 2.2%~6.5%，陈旧组 34.5%~48.0%。也就是说，一旦跨过 15 分钟，失败率就不再受并发影响。

### 1.4 决定性证据：青龙二区是同一批数据里的对照组

| | 陈旧请求数 | 陈旧请求失败数 | 失败率 | 陈旧占比 |
| --- | ---: | ---: | ---: | ---: |
| 青龙二区 | 65 | 4 | **6.2%** | 23.7% |
| 其余三区 | 199 | 103 | **51.8%** | 25.4% |

两边的陈旧占比几乎一样（23.7% vs 25.4%），说明青龙二区**同样被同步积压影响**，但它不因此失败。

再看失败率与剩余配额的关系（这是把「真的没货」和「校验拒绝」分开的关键）：

| 剩余配额 | 青龙二区（全部） | 其余三区（全部） | 青龙二区（只看陈旧） | 其余三区（只看陈旧） |
| --- | ---: | ---: | ---: | ---: |
| 0–5 | 31.5% (n=54) | 15.6% (n=141) | 30.8% (n=13) | 43.2% (n=37) |
| 5–10 | 3.5% (n=57) | 13.9% (n=115) | **0.0%** (n=9) | 45.8% (n=24) |
| 10–20 | 5.1% (n=79) | 13.7% (n=241) | **0.0%** (n=21) | 51.7% (n=60) |
| ≥20 | **0.0%** (n=84) | 17.1% (n=287) | **0.0%** (n=22) | **57.7%** (n=78) |

- 其余三区：快照陈旧时，**剩余配额越多反而越容易失败**（43%→58%）。这在业务上讲不通 —— 不可能是「卖完了」。
- 青龙二区：余量 ≥5 的 **52 次陈旧请求一次都没失败**，只有余量真的见底（<5）时才失败。这才是配额校验应有的形状。

> 我看不到代码，只能从行为反推：青龙二区大概率已经改成「扣券前读权威余量」的校验（灰度/对照组），其余三区还在用快照比对。这个推断是本文最重要的外部假设，已写进第 6 节。

## 2. 根问题

**扣券前的状态校验，用的是玩家/缓存侧的卡池快照，而不是服务器权威余量；同步延迟只是把这种不一致暴露出来。**

```
高峰并发 ↑
   └─> 卡池同步任务积压（全服更新，按区×池串行）      ← 观测：8.6% → 49.1%
         └─> 快照时延跨过 15 分钟                       ← 观测：双峰，25% 的请求落在这一侧
               └─> 提交时用旧快照校验 → 派发版本/余额对不上 → 直接判失败
                     └─> 玩家已点确认、券已锁，但没拿到道具     ← 观测：40.5% 失败率，与余量无关
```

三条证据都指向「校验口径」而不是「库存不够」：

1. 失败率在余量 ≥20 时依然高达 57.7%（其余三区、陈旧组）—— 有货也失败；
2. 失败率在时延跨过 15 分钟后陡然升高，且不随时延继续恶化而明显上升（33%→44% 后走平）—— 是门槛型拒绝，不是渐进式耗尽；
3. 同一个游戏、同一周、同样的同步积压，青龙二区失败率 6.2% —— 说明这不是物理约束，是实现选择。

顺带两个同源问题：

- **资源锁定不可回滚**：失败发生在扣券/锁券之后，玩家等完活动窗口才被打回，这就是客诉里「浪费等待时间 + 资源被锁」。
- **4.4% 的请求没有终态**（49 条 `is_success` 为空，其中 16 条落在陈旧区）：没有幂等流水和对账任务，这部分既无法补偿也无法复盘，风险敞口 3,675 点券。

## 3. 我做了什么

我没有改线上代码（拿不到），交付的是**可复现的归因 + 可直接落地的判定规则 + 回测**。

### 3.1 动作清单（按性价比排序）

| 优先级 | 动作 | 具体改法 | 预期 |
| --- | --- | --- | --- |
| **P0 治本** | 校验改权威读 | 扣券前对 `(zone, pool)` 做一次带行锁的余量读（或 Redis 原子 `DECR` + 落库校验），判定依据只认权威值；快照只用于展示 | 失败 143 → ≈84 次/7 天，约 **4,425 点券**，不阻挡任何成功招募 |
| **P0** | 幂等 + 对账 | 以 `log_id`/`request_id` 做幂等键；扣券、发货、回滚同一事务或补偿表；空状态 5 分钟内自动对账 | 消掉 4.4% 未决，止住「锁了不退」 |
| **P1 止血** | 陈旧即置灰 | 提交前若 `now - pool_synced_at > 15min`，先置灰 + 触发一次该池同步，同步回填后自动恢复 | 失败率 13.52% → 4.53%，净 **+2,745 点券 / 7 天** |
| **P1** | 低余量保护 | 权威余量 <5 时置灰并提示「即将售罄」，同时刷新 | 修好 P0 后剩余失败的 ~73% 集中在这一档，模型净收益约 +700 点券 / 7 天 |
| **P2** | 同步链路扩容 | 同步任务按区×池分片 + 增量推送（只推变化的池）；对 p95 时延设 15 分钟 SLO，超过 5% 请求陈旧就告警 | 把 25% 的陈旧请求降到 <5% |

### 3.2 判定规则（可直接抄）

```js
// 下单前
const snapshotAgeMin = (Date.now() - pool.syncedAt) / 60000;

if (snapshotAgeMin > 15) {
  ui.grayOut(pool);              // 置灰：不扣券、不锁资源
  syncQueue.trigger(pool);       // 立即拉一次该池权威数据
  return 'SYNCING';
}

// 扣券前（P0）
const authoritative = await quota.authoritativeRemain(zone, pool, { forUpdate: true });
if (authoritative < 1) {
  ui.grayOut(pool, 'SOLD_OUT');  // 真售罄，不是校验失败
  return 'SOLD_OUT';
}
const ticket = await lockResources(pool, { idempotencyKey: logId });
await deductAndGrant(ticket);
```

要点：

- **15 分钟是数据给的**：13~17 分钟之间没有任何样本，所以 12~17 任一阈值对这份数据的划分完全相同；取 15 分钟便于和同步周期对齐。
- **置灰 ≠ 关活动**：置灰只是拦截「扣券」这一步并触发同步，同步回填后自动恢复，不是让玩家等下一个活动窗口。
- **不要按并发拦**：并发 >70 置灰的命中率只有 19.5%，净收益 **-635 点券**（见 4.3）。并发是「因」，但不是可操作的判定变量。

## 4. 怎么证明有用

### 4.1 止血策略回测（全量 1058 条已判定样本）

规则：`快照时延 > 15 分钟 → 置灰（不扣券）`。收益 = 避免的失败 × 75，成本 = 置灰次数 × 20。

| 指标 | 现状 | 置灰后 |
| --- | ---: | ---: |
| 置灰次数 | 0 | 264（占 25.0%） |
| 失败次数 | 143 | **36** |
| 失败率 | 13.52% | **4.53%** |
| 置灰成本 | 0 | 5,280 点券 |
| 避免损失 | 0 | 8,025 点券 |
| **净收益** | — | **+2,745 点券 / 7 天** |

- 命中率 40.5%（每置灰 2.5 次挡住 1 次失败），**盈亏平衡置灰成本 30.4 点券/次** > 题设 20 点券，安全边际 34.2%。
- 代价要说清楚：264 次置灰里有 **157 次本可成功**，它们的招募被推迟到同步完成之后（不是取消）。如果产品不能接受「成功也被推迟」，那 P0 的权威读才是唯一正解。
- 未决敏感性：把 16 条陈旧未决全按失败算，避免失败 123 次，净收益 **+3,945 点券**；全按成功算仍是 +2,745。

### 4.2 时间外回测（防过拟合）

前 4 天（09-01~09-04）选阈值，后 3 天（09-05~09-07）验证：

| | 样本 | 失败率（前） | 失败率（后） | 净收益 |
| --- | ---: | ---: | ---: | ---: |
| 测试集，固定 T=15 | 473 | 14.80% | **5.52%** | **+1,530 点券** |
| 测试集，训练集 argmax T=18 | 473 | 14.80% | 6.30% | +1,365 点券 |

训练集 argmax 落在 18 分钟、全量 argmax 落在 13~16 分钟，相差 3 分钟；两者在 holdout 上都为正。**结论对阈值不敏感**，15 分钟不是调出来的。

### 4.3 对照：为什么不能按别的指标拦

| 策略 | 置灰数 | 避免失败 | 命中率 | 失败率 | 净收益 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A. 不处置（现状） | 0 | 0 | — | 13.5% | 0 |
| **B. 快照 >15 分钟置灰** | 264 | **107** | **40.5%** | **4.5%** | **+2,745** |
| C. 并发 >70 置灰 | 118 | 23 | 19.5% | 12.8% | -635 |
| D. 余量 ≤5 置灰 | 232 | 40 | 17.2% | 12.5% | -1,640 |
| E. 陈旧且并发 >55 | 154 | 67 | 43.5% | 8.4% | +1,945 |
| F. 陈旧或并发 >80 | 277 | 107 | 38.6% | 4.6% | +2,485 |

E 的命中率更高（43.5%），但漏掉 40 次失败，净收益反而更低。**「只拦最危险的那部分」在这里不划算**，因为陈旧组内部的失败率是平的（34.5%~48.0%）。

### 4.4 治本方案的外推（这是估计，不是实测）

用青龙二区按余量分桶的失败率套到其余三区（假设它的校验实现是目标状态）：

| | 现状 | 对齐青龙后 |
| --- | ---: | ---: |
| 其余三区失败 | 120 | ≈60.6（bootstrap 95% 区间 38~81） |
| 青龙二区失败 | 23 | 23（本来就是目标状态） |
| **全区失败** | **143** | **≈84（-41.5%）** |
| 折算点券 | 10,725 | ≈6,300（省 **4,425** 点券/7 天） |

这个数比 4.1 的 +2,745 更大，因为它**不牺牲任何一次成功招募**，也不会把玩家挡在门外。

## 6. 局限（我没有证明的部分）

1. **青龙二区是「对照组」是推断**。数据里没有版本号、没有服务器日志、没有 A/B 标记。我只能说它的失败模式（只随余量变、不随时延变）与「权威读」一致。要坐实，需要拿两个区的校验代码/配置对比，或看发布记录。
2. **没有真实余量流水**。「快照余量减去期间消耗」无法从这份数据还原，所以「失败与余量无关」是间接推断（余量越多反而越失败是反证），不是直接观测。
3. **4.4 节 -41.5% 是外推**，依赖「青龙的余量-失败曲线在其余三区同样成立」这一假设；bootstrap 区间给到 38~81 次失败，方向上稳健，量级有波动。
4. **置灰成本按「每次请求」计**。题设是「每提前置灰卡池一次 20 点券」，若实际按「每次池状态翻转」计费，成本只会更低、净收益更高。这份数据里陈旧请求在时间上高度离散（280 条陈旧请求分布在 276 个不同时刻，只有 4 个时刻出现 2 条并发），没有可合并的成簇，所以两种口径差别不大。
5. **未决 49 条**无法判定真实终态，已单独列出敞口；结论在「全算成功/全算失败」两种极端下方向不变。
6. **样本只有一个活动周期（7 天）**，没有跨活动的泛化验证；holdout 只能防阈值过拟合，不能防「这个活动特别」。
